## What's the big problem?
Regardless of how small your idea, it's scary to see just how many moving parts there are to configure, integrate, manage and debug in order to build the smallest thing, like an Appointment Booking System, for example.

Then add to that the monthly subscriptions and constantly changing Terms and Conditions, followed by the inevitable price increases. 

### Didn't low-code platforms solve these problems?
No they didn't, and AI made low-code obsolete anyway.

Consider these two points:
- **Low Code Platforms** - Write less code, but using an obscure scripting language that many AI models don't understand. You're locked into a black box, which hides many details of how things work.
- **AI** - Writes code just like people have been writing code for years. AI can write, test, fix and improve the code. There is no black-box. You're essentially leveraging decades of expertise.

Looking at the pros and cons of the above two points, it's easy to see how the dawn of AI was the death of low-code.

The biggest regret you will experience with low-code is being locked in to blackbox, a machine that does things, but users don't understand how, and often aren't allowed to see.

It's very common for people to start all over again when moving from one low-code platform to another, or from low-code to traditional code, where the ultimate transparency is found anyway.

Basically, low-code is just a new type of code, and only a handfull of people understand it. AI brought the focus back to traditional code, which millions of people understand, and you will be one of them.

You don't just build a solution. It has to run somewhere, securely and reliably. We often say 24 hours x 365 days. That's no mean feat!

You are being mislead if you've heard that AI is the solution to all these issues, as AI actually adds another layer of complexity.

How so? Well, AI is just more tech. But AI has the 'random' thing going on. The fancy way of describing that randomness, is hallucination where AI makes things up, and the fact that AI is `non-deterministic`, i.e. it doesn't create the same answer every time it's asked the same question. 

If you asked four different AI models to bake a cake, you would very get four different cakes, despite using the same ingredients. 

Each AI could have a different recipe book as it's source of information.

There are so many tiny detailed decisions that have to be made in order to construct a software solution, let's say it's an Appointment Booking System. If four people ask AI to help build this, there's a good chance everybody gets a working solution, but they won't be the same. 

Another point of view is that, AI enables you to build software, but it does not enable you to understand it.

### Is it a frontend or a backend.
We prefer to say it's neither. It's a toolbox. That will become clearer in a moment.

#### mAIcro is not a frontend
A frontend is the user interface. It;s where you see all the input boxes, charts, tables, reports, chat messages, notifications and documents.

But in the world of AI, the frontend is often not required. Because there is nobody interested in seeing the data. There is AI, doing it's job.

So ok, mAIcro isn't a frontend per se. But it does have an Integrated Development Environment (IDE), we call it an IDE because that's what developers have called it for years. And we don't want any new terminology that nobody understands, right?

#### mAIcro is not a backend
We don't call it a backend either, and this is in some part just to tease you!

You see, a backend is often just thought of as a database. A place to store stuff. Of course, it has logic too, what to do if X happens. Do Y.

But mAIcro is more than that, because yes it stores data, but it also interacts with things like websites, AI models, and it works with data in the traditional tabular sense (like SQL) but it also works with data which is graph like, a network of interconnected nodes. Naturally it also works with vectors, so stored data can used by AI, quick and efficiently.

SQL, Graphs, Vectors, these are all the bread and butter things that provide data that AI needs in order to do work.


#### Building blocks are tools
Many platforms come with a set of building blocks. Many, many blocks. But the building blocks in mAIcro are infinite. If there is something missing, you build it yourself and it becomes part of mAIcro.

All of this will become clearer in the training courses, where you will learn to use pre-defined building blocks, automatically generated building blocks, and then your own custom blocks.

- **Pre-defined** - These are tools that you use to create new database tables, new graphs, create nodes and connect them in the graphs. Or you can store documents and use them with AI. There are hundreds of pre-defined blocks.
- **Auto-generated** - These get created to simply managing data in your tables, like creating a way to add, update and delete customer records.
- **Custom** - When you need a connection to an external system, or want to make a complex task simple by wrapping it to become a reusable block, then custom blocks (wrappers) are the answer.

Now think of any building block as a tool. You want to create a table, there is a building block in mAIcro to do that. But now think of it as a tool, as that is how we would refer to building blocks when AI uses them.

So the building blocks in mAIcro have a one to one relationship with tools. AI <-> Tools <-> Building Blocks.

- **You** - "AI, create a customer table"
- **AI** - "Let's use the table create tool"
- **You** - "Create some example customers"
- **AI** - "Let's use the insert data tool for customers"
- **You** - "Show me the customers"
- **AI** - "I'll use the read customers tool to fetch the data from the customers table"

## **!!NERD ALERT!!**
It's time to get nerdy, just for fun, and this is where you might want to jump on to Google and search for a few technical terms. Firstly because it might be reassuring just how much information there is on the web to explain things and learn from. That goes to show you that mAIcro is not a blackbox, or another obscure scripting language.

Essentially, 99% of mAIcro is GraphQL resolvers. GraphQL is a language that every AI model understands. Nothing obscure there.
A resolver, is a piece of logic that does something required by a GraphQL operation, like a `query` which reads data, or a `mutation` which updates or deletes things.

If you get a basic understanding of what a resolver is, then you almost completely understand mAIcro. Every building is a tool, is a resolver, is a GraphQL operation, either a `query` or `mutation`.

## Normal service has been restored...
OK back to normal-people-speak!

What we just said, in a different way, is that everything that we want to do in a system, like managing a database, adding and updating data, or communicating with other systems, all needs something that does a small task. That task gets done by a resolver, which is a building block of mAIcro.

Data can not just magically appear. Somewhere there is some code that runs a database query. So a resolver looks at a GraphQL query, for example:

```
query {
  customers {
    name
    address
  }
}
```

Our simple query tells our customers resolver to get the name and address of all customers.

#### What goes on in mAIpads?
A key point, if you're familiar with coding, is that `#` in some languages means comment, i.e. some kind of documentation, small pieces of text that explain what the code is doing.

So anything which is not specifically a GraphQL statement is basically a comment. So this .gql file is a mAIpad, but it's really just a GraphQL script with lots of comments in which means anyother platform will ignore the comments.

But mAIcro gets a lot of information from these notes. From top to bottom:

- **Front matter** - this is a recent addition to Markdown, which means we can present some special information. For mAIcro the frontmatter tells us if this is a learning opportunity, and it might be for beginners or more advanced users. It might have a video on YouTube.
- **Sections** - In `.gql` files it's note necessarily clear if we have multiple operations, like inserting lots of new records, which ones will start and finish first. So the special STEP COMMENT - ###> SOME TEXT, seperates each thing that we want to run. Each step runs after the previous completed. 
- **Embedded Markdown** - #{ and #} indicate the start and end of a block of markdown. As you can see above, these indicators are wrapping documentation that explains each step.

Again, we have not really created anything new. We have drawn inspiration from Python Notebooks to blend code and documentation, so it's easy to keep everything up to date.

But mAIpads look spectacular when you view them in the IDE. You can see the 'code' of the script, and then you can view the whole thing as though it was a document / tutorial that teaches how the code works.

mAIpads present information when executed in the IDE. You can see how long things take to execute. What the data is that's being used as a mAIpad executes. You can see where errors occur.
